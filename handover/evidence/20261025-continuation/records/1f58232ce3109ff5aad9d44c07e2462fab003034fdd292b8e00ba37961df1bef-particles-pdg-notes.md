## 1. POP vs Vellum 粒子系统选型

- 点大小：`pscale`；点重量：`mass`。这两个再加上重力，进入粒子系统会产生向下坠落的粒子效果
- POP 粒子只和碰撞体产生弹性、摩擦力等**简单交互**；近看时点与点之间会穿插，没有任何互动关系
  （正是这样简单处理交互力，才能高效计算巨量粒子数据）
- 需要粒子与粒子之间真实碰撞，就要用 **Vellum 解算系统**：
  - Vellum 中每个点的 `pscale` 代表这个点真实的大小，依据 pscale 解算真实运动，
    可计算出真实的颗粒物效果
  - 相对 POP 会多计算：粒子之间的摩擦力、碰撞、弹力、吸引力、粘性力等
- **调整粒子之间的吸引力（attraction，黏性）**：可以模拟它是光滑的沙子，还是成块成堆的积雪
- 颗粒之间添加线连接 + 弹簧物理解算 → 模拟出**布料**
- 颗粒之间添加**表面张力**（Surface Tension：最外层粒子额外增加向内的拉力，最外层粒子
  互相之间像弹簧一样连接，尽可能向内收缩使表面积最小化）+ 重力 → 三个力
  （表面张力、重力、向内收缩力）交互 → 做出**像水一样的液体模拟**
- MPM 适合弹塑性材料和完全弹性材料（材料大变形）：雪、土壤、金属是弹塑性物体，
  混凝土同时具备弹塑性和脆性混合体

## 2. POP Network（DOP Network）内常用节点

- `POP Flock`：将群集算法应用于粒子，使粒子聚集在一起。此运算符修改 `force` 属性

### POP Source 参数速查

**Source 选项卡**：控制发射器类型和发射器几何来源。

**Birth 选项卡**——两种发射粒子的方法：

| 方法 | 行为 |
|---|---|
| Impulse | 每次节点烘焙时都会创建一定数量的粒子 |
| Const（常量） | 每秒创建一定数量的粒子 |

| 参数 | 作用 |
|---|---|
| `Impulse Activation` | 控制 `Impulse Count` 和 `Const. Activation`；值 0 = 关闭，任何其他值 = 打开 |
| `Impulse Count` | 每次节点烘焙（每一步幅）要发射的粒子数 |
| `Const. Activation` | 0 不激活 / 1 激活，打开和关闭恒定发射 |
| `Const. Birth Rate` | 每秒产生多少个点（不管任何参数只看总数） |
| `Max Sim Points` | 绑定几何体中点总数的上限，达到便停止发射 |
| `Max Points per Frame` | 限制每帧可以添加的点数 |
| `Life Expectancy` | 粒子存活时间 |
| `Life Variance` | 粒子存活时间 ± 多少 |

### 力类节点组合

- `POP Force`：对粒子施加力。在力场基础上增加噪波产生波幅
- `POP Drag`：将拖动应用于粒子——粒子移动的相反方向加拉力
  （但不会超过粒子移动方向的力），限制粒子的移动速度增加阻力
  - 典型组合：物体有速度场所以粒子向上移动 → `POP Force` 加噪波产生波幅 →
    `POP Drag` 限制移动速度
  - （截图见原笔记：QQ20250911-093024.png、QQ20250911-091319.png、QQ20241217-225015.jpg）
- `POP Advect by Volumes`：使用体积的**速度场**移动粒子。`SOP` 路径引入体积。
  `Advection Type`：
  - `Update Force`（更新力）：根据力比例和速度场调整粒子的加速度，就像 `POP Force`
  - `Update Velocity`（更新速度）：通过在速度场中混合**直接改变粒子的速度**，
    使它们快速匹配速度场
  - （截图见原笔记：QQ20250919-164310.png）
- `POP Wind`：将风应用于粒子。通过 `Wind Velocity` 设置风的方向和强度，
  就可以把粒子往那个方向吹
  - （截图见原笔记：QQ20250919-165703.png）

## 4. 粒子实战经验：1600 万沙粒

> 沙子的处理选择的是 vellum，感觉比用 `popgrains` 方便许多，一共跑了一千六百万的粒子。
>
> - 颜色处理上要注意**个别特别明亮的沙砾**；整体 ramp 需要花时间调整，这将影响整个沙子的表现

>   缩放了 `0.75–1.35`，同时又随机选择一部分粒子让其 pscale **再缩放一倍**，
>   以增加更大的颗粒

>   增加更丰富的结果
> - 以上操作在大景别可能看不出来，但当镜头比较近时会带来非常多的细节，
>   **哪怕沙子精度本身比较低**

## 6. PDG / TOPs

### 概念速查

- PDG（Procedural Dependency Graph），Houdini 17 推出。字面翻译为**程序化依赖图表**：
  PDG = 所有的任务及其中蕴含的依赖关系
- PDG 优势之一：**任务调度和多线程高效执行**——可以让 Houdini 时时刻刻跑满 CPU，
  节省很大一部分时间
- Height Field 地形、程序化植被、道路等程序化数据通过 Houdini Engine 在游戏引擎中以
  HDA 形式存在，**PDG 最大的意义便是将这些 HDA 资源统一调度管理**
- PDG **是一种程序架构**（独立 API 接口），旨在分配任务和管理依赖关系，扩展、自动化和
  分析影视/游戏/广告/VR 内容管道；TOPs 是应用于 Houdini 的 PDG 技术（类比 SOP、DOP 的节点系统）
- Houdini 节点工作流常被称为 `pipeline-in-a-box`；使用 PDG 可以打破这个框，
  组织和安排任务后智能分发到计算场并行工作
- **楔入（Wedge）、Prop 变体**：PDG 关键工作流程，快速创建设计的多个迭代，输出联系表
  评估迭代或选择多个 prop 变体丰富场景
- 借助 PDG 可合成/增强大量数据帮助**训练深度学习系统**，并同时尝试多个超参数
- 可用 Python 创建自定义解决方案或编写自己的 TOP 节点
- **PDG 可以使用现有调度程序（Tractor、Deadline、HQueue），但其本身并不是调度程序**：
  PDG 只告诉调度程序哪些任务已准备好处理，由调度程序匹配硬件资源
- 底层原因：**解算是基于上一帧的**（第一帧算完才能算第二帧），而**渲染帧与帧之间不存在
  依赖关系**，只要硬件资源足够，所有帧可以无序进行

### 关键节点

| 节点 | 作用 |
|---|---|
| `waitforall` | 等待上述全部完成后执行 |
| `wedge` | 更改某个参数多次，分别输出相应结果（如 box 宽度 1→10 输出 10 种形态）；加多个 wedge 实现 N 种不同组合 |
| `Local Scheduler` | 本地调度器，设置在本地计算机上计划工作项 |
| `ROP`（TOP） | 渲染此网络内的所有渲染节点，用布线连接表示渲染依赖关系 |

### 案例：RopGeometry 单线程节点加速（榨干 CPU）

背景：`remesh` 节点是**单线程节点**（重新拓扑模型布线）。一个球 + 随时间变化的
`mountain`，每帧 remesh 输出 20 帧缓存——8 核 16 线程 CPU **只占用一个线程**。
（截图见原笔记：QQ20241108-212757.jpg）

解法（新建只含一个节点的 PDG 网络）：

1. 新建一个 `TOPnet` 模块，在内部创建 `ropgeometry` 节点
2. `SOP Path` 指向需要输出缓存的 `remesh` 节点；`Evaluate Using` 改为 `Frame Range`，
   设置 1 到 20 帧的输出
3. `local scheduler` 设置最大 CPU 使用率（`Total Slots`，见下）
4. 点击 `Cook the output node's work items` 执行——指定线程全部被利用，CPU 100%
   （截图见原笔记：QQ20241108-213318.jpg）

**`Total Slots`（可用槽数）四种设置**：

| 设置 | 含义 |
|---|---|
| 默认 `0` | 总逻辑核心数 ÷ 4 |
| 负数 | 总逻辑核心数 − 该数字（如 `-1` → 16−1=15 核） |
| 自定义插槽计数（正数） | 使用"自定义插槽计数"字段中指定的数字 |
| 等于 CPU 计数减 1 | 逻辑内核数 − 1 |

（截图见原笔记：微信截图_20240216210017.png、微信截图_20240216210056.png、微信截图_20240216210227.png）

> 一个节点只能占用一个线程。使用 PDG，就可以利用多个逻辑核心同时进行多帧输出。
> 在无法充分利用硬件资源的场景下，使用 PDG 可以大大提高生产效率！

## 7. 渲染底层原理（CG-TD 基本功）

**Ray Casting**：

1. 从眼睛位置向每个像素投射光线，和场景相交，每条光线找到最近交点
2. 交点和光源连线判断是否对光源可见（该点是否在阴影里）
3. 算着色，写回像素

**Ray Tracing**（Whitted-style）：

1. 光线生成
2. 光线在空间中传播进行多次反射或折射
3. 计算所有弹射点的着色，将着色叠加，写回像素

**Path Tracing**：Ray Tracing 的一种应用，解决 Whitted-style 的两个问题——
无法处理 glossy 物体、在漫反射物体表面停止。Path Tracing 有正确的数学解释：渲染方程。

**Ray Marching**：

1. 光线生成
2. 光线在传播路径上按一定步长步进前进
3. 颜色计算，写回像素

常用于体素渲染：颜色计算过程为（2.1）获取当前位置密度、颜色；
（2.2）根据密度对颜色累积，写回像素。

## 易错点

- **粒子穿插无互动是 POP 特性不是 bug**：点与点之间没有交互关系；要真实碰撞/摩擦/
  粘性必须换 Vellum（或 MPM 做弹塑性大变形材料）。
- **`Impulse` vs `Const` 发射**：Impulse 是每次烘焙发射（按步幅），Const 是每秒发射；
  粒子总量不对先核对 `Const. Birth Rate`（只看每秒总数）与 `Life Expectancy` 的乘积。
- **`POP Advect by Volumes` 两种 Advection Type 差异大**：`Update Force` 类似 POP Force
  （改加速度），`Update Velocity` 直接混合改速度（快速匹配速度场）——想要"被风带走"
  用后者，想要"受风影响"用前者。
- **粒子渲染巨大**：默认 pscale 太大，Point Wrangle 里 `@pscale = 0.001` 一行修掉。
- **沙粒近景没细节**：即使解算精度低，也要做三件事——pscale 随机化（0.75–1.35 再随机
  翻倍）、instance 替换 ass 资产、随机毛玻璃材质；同时警惕个别特别明亮的沙砾破坏整体 ramp。
- **PDG 不是调度程序**：它只报告就绪任务；真正分发靠 Local Scheduler / Tractor /
  Deadline / HQueue。
- **Local Scheduler `Total Slots` 默认只有 1/4 核**：默认 0 = 逻辑核数÷4，想跑满要设负数
  （如 `-1`）或自定义正数。
- **单线程节点（如 `remesh`）直接 ROP 输出只吃一个核**：放进 TOPnet 用 `ropgeometry`
  + Frame Range 才能多帧并行榨干 CPU。
- **DOP 缓存经 `out`/`FileCache` 输出**：记得勾 `Initialize Simulation OPs`，
  否则 DOP 模拟不自动初始化。
- **刀光拖尾选型**：优先做 HDA 小工具（UE5 实时改、无缺点）；Trail ABC 法在动作本身
  有问题时几乎无法修正。
