## 本次发现

以下是基于现存记录的工程判断，不是新取得的真实运行结论：

1. **可行性被提前当作确定前提。** 可靠控制软件、把视觉要求映射为领域工程、有效反馈和跨案例复用，是分别需要证明的能力；第一项成立不会自动证明其余项。
2. **工作类型长期混用。** 已实现代码的错误、缺失功能、未确定的原生事实/算法、尚待判断的视觉效果，被统称为“返修”。应逐项分类，不能把研究任务按普通缺陷承诺收口时间。
3. **阶段存在实际依赖矛盾。** M1 剩余项要求实际 writer 和下游消费事实，但真实验收手册要求 M1 接收后才运行。部分事实仅靠静态原件和软件替身不能取得；继续重复软件回归不会自动补齐。
4. **全面铺开早于代表链路被证明。** 全域、双版本及通用基础设施同时推进，增加了集成面；当前记录尚不能证明同一冻结候选的完整创作闭环。
5. **验证投入与用户价值脱节。** 回归、签名、安装和包校验保护重要边界，但必须说明其消除了哪个真实使用障碍。数量增长不能作为接近创作成功的替代指标。
6. **并行缺少稳定的整体验证目标会增加整合工作。** agent 应围绕同一链路的明确阻断分工；不能各自制造局部成功后，由主控推断整体成立。

实施负责人需对范围核对、接口稳定、集成顺序和结论负责。不得把这些问题归因于用户未授权真实作业；应提前说明哪些事实无法在当前授权内取得。

## 怎样找到值得验证的闭环

从一个用户能直接使用的交付物逆向拆解，不从已有测试或模块数量开始：

1. 冻结合成参考、目标差异和交付要求：例如可编辑 HIP/NK、指定活动帧、反馈前后结果，以及哪些项目由人判断。
2. 对每一步写出“谁消费什么、产生什么、由谁验证”。下游必须读到上游实际产生并登记的版本，不能只记录名称或文件存在。
3. 在当前正式入口标出第一处缺失：配置/接口、代码、原生事实、真实执行、视觉判断分别归类。明确解决此项后能推进到哪一步。
4. 优先选择不确定性集中、资源可控、能留下可编辑产物的代表链。不得靠删去关键阶段制造闭环；若只能完成一部分，就只报告该部分。
5. 将正常、反馈、恢复和复用分别判断。一次正常成功不证明恢复；同一案例改数值也不足以证明跨域组合。

需要证明的主链为：**登记参考 → 实际附件/观察 → 分域控制计划 → 正式建图 → 保存和新进程重开 → 有界预览 → 反馈及新版本 → 登记实际产物 → Nuke 消费和交付 → 人工判断结果。** 涉及真实宿主、模型、cook/求解或输出执行的阶段均须事先满足对应授权；当前只在已授权软件边界内推进。

5. **预检边界：**16 卡当前均为 `native_basis_status=UNRESOLVED`，预检仍会报 `native interface basis unresolved`。已完成 [案例选择与逐卡版本约束修复](KARMA_PREFLIGHT_20261016.md)：依据合法 case_ids 选择基础/反馈/恢复案例，在全局可识别版本内落实卡片 required_versions，保留旧单案例卡及显式旧版卡。仅这两项软件修复不能使原生预检通过，不改状态标签绕过。
6. **参考输入边界：**进入 HY3 门前需核对实际参考。默认生成的两张图及当前受控分析登记限 synthetic，符合本阶段隐私要求；应登记有实际目标内容的合成参考，不能把默认演示图当作任意参考能力。未来非合成参考须另外确定来源、隐私和正式接入，不能只换素材字节却沿用 synthetic 声明。
7. **路线文档差异：**[testing-and-live-validation.md](../docs/testing-and-live-validation.md) 的豆包模型段落属于历史路线。当前要求以 WorkBuddy/HY3 手册和 STATUS 为准，历史模型结果不能替代当前路线。

## 真实运行授权和资源确认

当前路线调整只改变活动工作的依赖顺序，不批准 M1 接收前真实实验例外，也不调整原生预检或真实宿主验收前置条件。所需事实不能在当前软件边界内取得时，记录具体 BLOCKED；真实阶段仍须满足现有条件并另行明确授权。

一次具体申请需冻结：

- 当前源码/安装包指纹、域与 case、task/session/request/内容版本，以及要回答的一个问题。
- 宿主精确版本、可信可执行文件和插件 build；是否涉及 WorkBuddy/HY3、外部模型或媒体传送。
- 任务目录、输出/临时/日志根、磁盘上限和最多运行时间；单个公开短作业最多 12 个明确帧、120 秒。申请还需明确总实验作业数和累计上限，不能换 request ID 绕过约束。
- 是否建图、cook、求解、缓存、渲染；各项单列，不能把“只读采集”扩展成执行。仿真另列必要历史；缓存另列帧段、路径、估计占用、内容版本和失效范围。
- 仅处理哪些已登记合成媒体和获准派生内容；谁作视觉判断、在哪里留原始证据。
- 如何停止自有进程和恢复；同时最多一个重型作业，未知停止继续占槽，不关闭预先存在的用户进程，不自动删除用户文件。

若门槛或授权不足，报告 BLOCKED 和所需的精确事实/决定；不能直接调用原生 API、改 `native_basis_status` 或禁用预检来绕过。

## 每次实验如何判定

沿用现有状态，不另建支持等级：

| 状态 | 使用条件 |
|---|---|
| PASS | 该次声明的全部阶段实际发生，输入/操作/产物/消费和源码绑定齐全，并满足事前约定的判断标准；仅在该次范围内成立 |
| FAIL | 已执行且违反冻结的结构、行为、资源或视觉标准；定位最早失效阶段 |
| BLOCKED | 缺实现、原生事实、合法输入、依赖或授权，无法合法完成该次实验；说明具体阻断和下一动作 |
| NOT_RUN | 该阶段未执行；已发生的局部事实单列，不能把整条链写为通过 |

判断标准在实验前确定。除已有 12 帧/120 秒等约束外，本文不擅自新增成功率、视觉相似度或人工次数门槛。时间、费用和介入上限尚未约定时，记录实际测量值，不能声称经济性已通过。

每次保留一个可独立复核的记录，至少包含：

- 输入媒体 ID/hash、时间或帧、目标、未知信息、原始用户反馈；第二例还要写明相对首例的实质差异。
- 当前 build、安装/启动来源、正式入口和具体 case；软件/原生/模型/人工各自的事实来源。
- 各阶段 operation/request、宿主身份、场景/产物版本、artifact ID/hash 和实际下游消费依据。
- 保存与冷重开的结构/参数/连接，反馈前后版本和失效范围，动态帧以及 HIP/NK/结果的相对位置。
- 中断的实际 worker、监督器停止事实、重启恢复过程、是否重复副作用，以及停止/账本/槽的分别状态。
- 总耗时、机器执行与等待、人工操作时间/次数及具体动作、模型/渲染成本、峰值存储、失败重试；没有数据的字段明确 unknown。
- 视觉判断者、事前约定的目标、通过/未通过理由和原始图像/序列。像素变化只证明变化，不证明正确运动。
- 阶段结果、最早失败点、已知限制、独立复核范围，以及是否需要软件整改或另行实验。

手工修改工程、补元数据或替换产物的动作都要计入介入记录。不能把人修好的结果写成 agent 自动闭环，也不能把同一案例的多次失败隐藏为一次成功。
