# Tutorial reconstruction and inherited scenes

Use the tutorial's visible target and the user's requested coverage to define success. A minimal simulation is a milestone, not permission to omit later chapters. Read the video at the relevant timestamps as well as the transcript; inherited summaries and ASR are fallible evidence. Establish whether the tutorial builds from scratch or demonstrates an existing system, and identify any required author assets before promising equivalence.

Record a compact target table: tutorial timestamp, visible behavior, required inputs or modules, reproduction method, matching existing case evidence, cheapest discriminating test, and evidence still missing. Label substitutions and estimates. Do not silently replace an unavailable authored system with a generic pack and declare the tutorial reproduced. Missing reusable author assets may be rebuilt using registered capabilities; report specific gaps when that route is unavailable.

## Assess before committing

Distinguish a step-by-step tutorial from a showcase or a demonstration of a
prebuilt system. For each required component, record whether its construction
is visible, depends on supplied assets, or needs an unproven reconstruction.
Unreadable values and hidden subnetworks remain unknown; do not invent them.
Extract only enough frames, text and node detail to resolve the current
decision, then return to making the requested result.

Check the active route's actual tools, node versions, inputs and relevant case
evidence. Classify the proposed work as an established workflow, an experiment,
or blocked by a concrete missing dependency/capability. An untested component
is not automatically unsupported. Explain uncertain coverage before promising
delivery, without reducing the user's target. If execution is requested and
authorized, start the cheapest useful test after this brief assessment.

## Use a bounded learning loop

Recover the current candidate, last decisive failure and remaining task budget
before a new trial. Carry time, launches and unresolved operations across
retries and handoffs; a new request ID or directory does not renew permission.
Use the task's limits rather than copying numbers from an unrelated example.
When a stop condition is reached, stop new experiments and retain the best
honestly labelled result. More budget alone is not evidence that the route
will converge.

For each experiment, state the suspected cause, one main change, a comparison
baseline and the observation that would distinguish success from failure.
Check available parameter values, serialization and input contracts before a
costly launch. Inspect source shape, selected region and motion before tuning
a solver. Reuse valid upstream work and run only affected consumers.

Choose official documentation or a relevant worked example to answer a
specific unresolved question. Translate it into a testable operation on the
installed version. Record what changed, whether the measured and visible
result improved, what was ruled out, and why another trial is justified.
Repeated non-improvement without new evidence requires revisiting the cause
or approach, not repeating the same adjustment. A launch or script failure is
not evidence about the proposed physical fix.

Keep task-local observations separate from reusable conclusions. An observed
failure can establish a diagnostic pitfall within its tested conditions; it
does not prove all variants of a technique fail. A successful repair needs
matching before/after evidence and compatibility limits. Updating instructions
does not change a domain's support status. Formal KnowledgeCard or
RepairExperience promotion still follows its own approval contract.

Mark cuts, replays and speed changes before mapping visible events to the
project timeline. Keep the video timestamp, the frame shown in the tutorial
and the chosen target frame separate. Where the time mapping is unclear,
use the order of events and any duration range the evidence supports. Mark
each row as directly observed, inferred or a local reproduction choice.
For an unreadable parameter or a hidden subnetwork, describe the behavior
the substitute must reproduce and how its output will be measured.

For each dependent layer, name the upstream artifact, the consumer and its
required frame range and attributes. Name the saved observation that will
pass the layer. Bind the stage to a registered recipe or supported action
after checking the actual catalog. Where the implementation is unavailable,
keep the layer in the plan and report the missing capability. A substitute
input can qualify the wiring; shot acceptance uses the accepted shot input.
Use the earliest failing producer and its direct consumer for the next test.
Recheck a downstream cache only when the change affects its input contract.

Before loading an inherited HIP, preserve its bytes and inspect dependency/trust metadata. Use a task-owned environment under the established trusted or isolated loading route; never replace another task's GUI scene. If ownership or safe loading cannot be established, work from a clean task-owned scene or request the concrete missing setup. Files supplied for local reference are not automatic permission to upload them to another model/provider.

## Make each trial explainable

- Name the actual display/render endpoint and trace its input role and live/cache source. Compare current candidate identity, frame set, parameters and upstream inputs with the cache subject. Distinguish live, valid cache, stale cache and unknown. Invalidating a ledger entry alone does not prove a disk-reading node stopped serving old geometry. Do not delete caches as a diagnostic shortcut.
- Before tuning an event, record fps, scene start, simulation start, global versus simulation time, units, and whether the control is an impulse, target velocity or acceleration. Verify the event before/inside/after its window. Tutorial frame numbers and numeric forces are examples, not portable defaults.
- Keep rest, animated, fractured, simulation and render geometry roles explicit. Check required geometry/constraint streams and topology compatibility before expensive solving or high-resolution deformation. Diagnose empty/degenerate/non-finite output before increasing forces or solver quality. Use scale-aware evidence rather than universal cleanup constants.
- If an edit has no visible effect, first distinguish inactive input, stale cache, inactive time window, disconnected force/constraint path, and wrong display endpoint. Test one cause family with an owned reversible candidate. Do not keep increasing power or stiffness without establishing that the change reaches the output.
- Use exact persistent operation IDs for slow calls. A timeout is not proof of nonexecution. Do not retry a cache button, rebuild, or start another heavy job until the earlier operation is accounted for.

## Compare and deliver

Use the same camera and timeline for baseline/candidate comparisons, with a playable sequence covering onset and aftermath. Inspect simulation geometry and final surface separately. Single close-ups, node counts and successful writes cannot establish the requested motion or visual match.

Prefer a low-cost motion preview before expensive shading or final rendering.
Check that the same body parts, event order and visible extent as the reference
are represented. A smaller stable test is useful diagnostic evidence, but its
omitted components remain outstanding. Check final-surface contact separately
from solver metrics; positive tetrahedral volumes do not exclude penetration.

Preserve the user's complete goal while staging work: source/animation, fracture/constraints, event/motion, surface transfer, secondary effects, shading/render. Track every requested tutorial component as demonstrated, partial, blocked or untested. Cache approval remains separate and binds the actual artifact type and dependencies; a surface export is not automatically a resumable simulation cache.

Deliver editable project(s), available dynamic previews, settings/versions/dependencies, exact compared timestamps, and known visual differences. Name the execution interface that produced the evidence. An operator-scoped worker can establish a shot result while the registered model-facing path still needs its own trial. User visual acceptance remains distinct from software and DCC execution checks. Do not present a Codex execution trial as GLM or WorkBuddy/HY3 model acceptance.
