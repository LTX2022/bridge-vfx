# Verification and support status

A task result is acceptable only when required artifacts are present, non-empty, readable, traceable to their producing run with dependencies still matching the current task, connected to the intended component lineage, and produced by an editable graph. The target issue's pack metrics must improve without violating protected dimensions, followed by artist confirmation.

## Task acceptance

Use the user's complete target and requested frame range as the checklist.
Keep the following evidence separate; passing one row does not imply the next.

| Claim | Required evidence |
|---|---|
| Tutorial understood enough to attempt | Observed key events and steps, mapped inputs, explicit hidden or uncertain parts |
| Route can perform an operation | Current exposed capability, required assets/configuration and authorized scope |
| Native step passed | Actual non-empty output, case-specific checks, matching frame/build and terminal operation evidence |
| Motion/geometry passed | Relevant full frame segment, onset and aftermath, topology/shape/contact and intended event checks |
| Reference effect reproduced | Comparable sequence and key-frame observations for every requested component, with remaining differences stated |
| Deliverable works independently | Saved editable project reopened from the delivered location, required dependencies resolved, output clip decoded over the requested range |
| User accepted the result | User/artist confirmation; do not invent it from internal metrics |

A case may be technically delivered while visual acceptance is pending.
Technical `COMPLETE` or positive solver metrics alone cannot support the claim
that a full reference was reproduced. For each requirement, report passed, failed, not run or insufficient evidence,
separately from full-goal and visual acceptance. Reuse verified artifacts when
their dependencies remain valid; do not require regeneration just to obtain a
new run ID. Saved geometry proves playback only after readback;
solver continuation additionally needs a compatible cold-loaded state and an
overlapping comparison with continuous execution.

When stopping incomplete, deliver the best usable partial result and its
dependencies, first known failing frame/stage, tested changes and unresolved
conditions. State whether the delivery copy was reopened and what requires
the original workspace. Keep diagnostics in the report, not in the finished
creative output. Confirm owned processes stopped; an uncertain operation
remains unresolved and must not be replayed.

For temporal issues, evaluate the declared frame set and motion evidence. Never claim recovered physical speed or dynamics from a single still.

Domain maturity is evidence-bound:

- `experimental`: implementation exists but contract evidence is incomplete.
- `contract-tested`: schemas, safety, and deterministic fixtures pass.
- `live-validated`: a matching DCC/model build produced machine-readable artifacts.
- `supported`: all declared versions and required real cases pass and are indexed.

Software tests or a successful bridge health check do not make a domain `supported`. Missing model credentials, a DCC license, a required node/parameter, or a real reference case remains an explicit release blocker.

Bind capability evidence to its route, software build, inputs and tested case.
A direct operator-script result does not qualify a model-facing tool route;
a static modeling case does not qualify a coupled simulation or arbitrary
tutorial. Keep case evidence in project results rather than hard-coding a
changing capability inventory into this skill.
